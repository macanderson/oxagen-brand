The problem

A process made for people

Most teams build software the same way. A person writes a change. Another person reads it. They talk, fix it, and wait. Then the change ships. Each step fits a person's work day.

Agents do not have a work day. They can work at any hour. But the old process still stops at every step to wait for a person.

The agents' rules

  1. Every change starts as an issue, and the issue says what done looks like.
  2. A triage agent sets each issue's priority and size. Whoever files the issue does not.
  3. One change has one writer. An agent posts a claim before it writes, and the claim lasts 90 minutes.
  4. Automatic checks are the only place Oxagen's code is built and tested.
  5. An agent looks at each open change every 60 seconds. It fixes failed checks, answers review comments, and clears conflicts.
  6. Review findings are rated P0 to P3. A P0 blocks the change. Leftover small findings go into one follow-up issue.
  7. When main breaks, a check opens a P0 issue. The fix goes straight to main, and the check closes the issue when main is green.
  8. A database change carries a label. The checks apply it when the change merges, before the code that needs it goes live.
  9. Each run ends with a note on the issue: minutes planned, minutes spent, and what the next agent should know.

Oxagen's role

Oxagen is workforce management for autonomous agents. It is the part of this process that manages the agents themselves.

Identity

Each agent gets its own identity. Agents do not share an account.

Mandate

Each agent works under a mandate: its access, its budget and rules, and its tools and skills.

Rules

When an agent asks to do something, a rule answers: allowed, denied, or routed to a person.

Record

For actions routed through Oxagen, the record shows what each agent did and what it cost.

The process

The ten stages

Each change moves through ten stages. Agents run all ten. People come in where a rule says so.

01

Issue

Agent or person

Every change starts as an issue. It says what is wrong, which files to change, how to check the work, and what done looks like.

RuleNo issue, no change.

02

Triage

Triage agent

A triage agent sets the priority, the size, and the area. Whoever files the issue adds only one label: triage.

RuleThe filer does not set the priority.

03

Claim

Agent

Before an agent writes, it posts a claim on the issue or the change. The claim lasts 90 minutes, and the agent renews it while it works.

RuleOne change, one writer.

04

Build

Agent

The agent starts a branch from the latest main. It makes the change and adds tests for it. Then it opens a pull request that names the issue.

RuleTests ship with the change.

05

Check

Automatic checks

Checks build and test every push. When a check fails, an agent reads it right away and pushes a fix. Nobody runs a check again just to hope it passes.

RuleChecks are the only place code is built and tested.

06

Review

Review agent

Review agents rate each finding from P0 to P3. A P0 blocks the change. Small findings left over go into one follow-up issue.

RulePass 1 fixes P0 to P2. Pass 2 fixes P0 and P1. Later passes fix P0.

07

Merge

Agent

A change merges when every check passes, no P0 or P1 finding is open, and nothing conflicts with main.

RuleGreen checks and no open P0 or P1.

08

Release

Automatic checks

A merge to main deploys. A database change carries a label, and the checks apply it before the code that needs it goes live.

RuleThe database change goes first.

09

Watch

Automatic checks

When main breaks, a check opens a P0 issue. The fix goes straight to main. The check closes the issue when main is green again.

RuleThe time in between is the recovery time.

10

Learn

Agent

Each run ends with a note on the issue: minutes planned, minutes spent, what shipped, and what the next agent should know.

RuleEvery run leaves a note.

People

People's role

People own every change. Each agent run has a named operator. The operator does not read every line. The operator sets the rules and reads the record.

Rules

People write the rules before the work starts. Security writes the access rules. Finance writes the budget rules. Engineering picks the tools and the checks.

Decisions

A rule can send a request to a person. Spending over a budget, adding a new tool, and reading production data are common ones. The run waits for the answer.

Record

Each day, the operator reads what shipped, what is waiting on a person, what broke, and what it all cost.

Dropped tasks

  • Reading every line of every change
  • Running checks again by hand
  • Chasing status
  • Merging by hand

Adoption

Rollout plan

Start with one repository. Move one step each week.

  1. 1

    Rules

    Pick one repository. Write the rules. Give each agent its own identity.

  2. 2

    Checks

    Move every check into CI, the automatic checks. Make CI the only place code is built and tested.

  3. 3

    Review

    Turn on review agents and the pass rule. Let agents merge a change when the checks pass and no P0 or P1 is open.

  4. 4

    Record

    Read the record each day. Count merges, hours, recovery time, and cost per change. Change the rules that slow the work.
