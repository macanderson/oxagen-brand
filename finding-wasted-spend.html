Proposal

Finding unproductive spend

Your agents pay for steps that buy no progress: a status poll that returns the same answer, a cache that expires while a parent run waits, a complex-class model on a job that only reads. This page proposes eight detectors Oxagen can run on the record it already keeps. It ranks them against a measured week of agent usage and names the data each one still needs.

Summary

Summary

  • The request is the unit of waste. Cache reads were 57% of the sample. A wasted step costs the full context re-read it forced, so every detector here prices a step at the request that carried it.
  • Spin and poll loops rank first. Thirteen subagent runs spent 10.9% of the sample on calls that returned the same answer. The shipped duplicate_tool_calls finding priced every repeat in the sample at 0.02% of spend. Priced at the round trip, the same repeats cost 12.1%.
  • Standing context is the largest line. Re-reading each run's first context cost up to 16.5%. Each 1,000 tokens sent on every request cost $29.11 a week at this volume, so a weekly price beside each tool provider and each steering record makes the trade visible.
  • Seven of the eight detectors work on digest-only workspaces. Only prompt habits needs prompt text, which Oxagen keeps for workspaces on content_exact.
  • Three detectors wait on capture. Standing context needs the ADR-062 token fields. Cache busts need a per-turn digest of the system context. Spend with no outcome needs the PR, CI, and revert join.
  • Managers see operators ranked by unproductive spend. Proposed figures beside each name separate waste from volume: unproductive share, done work orders, and unassigned share. Output counts only work orders whose definition of done passed.
  • Nothing on this page changes an agent by itself. Each lever is a steering record PR, a setting, or a rule the owning team sets, recorded in observe mode before anything is enforced.

Decided

  • The product term is unproductive spend. The filename keeps the word the request used.
  • Every call contributes to at most one finding (packages/billing/src/findings.ts).
  • Spend and habits are reported per operator, per agent, and per workspace. Each habit is written as a rule the operator can adopt, with its definition beside it.
  • Managers see operators ranked by unproductive spend (see Operator productivity). This revises D15.
  • Price a repeated or wasted step at the request that carried it.
  • Add a no-progress limit the owning team sets, observe mode by default.
  • Show a weekly price beside each tool provider and each steering record.
  • Count only whole requests in the headline total (see Counting).

The review of 2026-09-27 approved the operator ranking and the last four.

Open

  • Whether the no-progress limit ships with a default. The sample used 20 unchanged repeats.
  • Whether unassigned spend counts inside unproductive spend. This page keeps it on its own line.
  • How long a direct work order has to be attached to a work item before its runs count as unassigned. One option is 24 hours.
  • Whether a work order counts as done at its passing check or at a person's acceptance. This page counts at the passing check.

1

Spin and poll loops

Ships in partdigest_onlyEfficiency

An agent runs the same call again and gets the same answer: a no-op shell command while it waits, a status poll that has not changed, or a retry that fails the same way. Each call costs a full request.

10.9%of the sample, spent by 13 subagent runs
Sample
  • 78% of those runs' requests ran only a no-op command, such as true, echo ok, or sleep 1.
  • The largest run made 3,590 no-op calls in 1.9 hours and spent 4.7% of the sample by itself.
  • Status polls with an unchanged result made 574 calls, at 0.45%.
  • All 13 runs were subagents on Sonnet 5, waiting on something another run would finish.
Lever
  • DecidedPrice duplicate_tool_calls and repeated_shell_commands at the request that carried each repeat.
  • DecidedAdd a no-progress limit, a rule the owning team sets, such as "pause after 20 unchanged repeats". The limit starts in observe mode, which records each hit. Enforced mode pauses the run at the next checkpoint, on governed calls.
  • Propose a steering record that tells agents to wait with the harness's own wait or a subagent result, and to stop polling in a shell loop.
Finding text

<agent> ran <call> <n> times in one run with an unchanged result. The round trips cost <amount>.

Signals
tool_name, input and output digests, tool_is_mutating, tool_error_class, session_files digests, request cost
Formula
A repeat is a call whose tool, input digest, and output digest match an earlier call in the run, with no mutating call or file change between them. Its price is the carrying request's cost divided by the tool calls in that request. A loop is 20 or more repeats in a row, the threshold the sample used.
Retention
Works on digest_only. Digests prove the repeat without the text.
Today
duplicate_tool_calls and repeated_shell_commands ship. Each prices a repeat at its result tokens with a counterfactual of zero. Retry loops is a specced cause with no detector.
Gap
Failed calls carry no billed tokens, so a retry storm that fails reads as free.
Why first
It applies to every harness, the data exists on every workspace, and it has a live lever.
2

Standing context

Specceddigest_onlyEfficiencyPerformance

Every request re-sends the same prefix: the system prompt, every tool definition in the toolbelt, and the steering stable prefix. Caching makes each re-read cheap, and the re-read still happens on every request, so a small prefix becomes a large line.

16.5%of the sample at most, re-reading each run's first context
Sample
  • The first request of a run carried 49,080 tokens of context on average.
  • Each 1,000 tokens sent on every request cost $29.11 a week at this volume.
  • At that rate the steering budget's default of 4,000 tokens costs about $116 a week.
Lever
  • DecidedShow a weekly price beside each tool provider in MCP Studio and each steering record, computed from the fleet's request count.
  • Move a provider whose tools agents rarely call from All tools sent to Searchable.
  • Hold the stable prefix to the steering budget, and name the record that pushed it over.
Finding text

<provider> adds <n> tokens to every request. Agents called <k> of its <m> tools this month. Its definitions cost <amount> a week.

Signals
Cache read tokens per request, first-request context size, tools_available, mcp_servers, tool_name per call
Formula
standing_tokens × read_price × (requests − 1) per run, split by source once the source fields report. Weekly price per 1,000 tokens: 1,000 × read_price × requests_per_week.
Retention
Works on digest_only. It reads token counts only.
Today
The steering budget (4,000 tokens, warns only), the MCP Studio definition budget, Searchable toolbelts, and the line for tools imported and never called are specced. The Optimization page names tool definitions over 16% of input.
Gap
tool_definition_tokens, context_frame_tokens, and steering_tokens are always null (ADR-062). The total cannot be split by source, so the sample figure is an upper bound that includes the first prompt.
3

Cache expiry and busts

Ships in partdigest_onlyEfficiencyPerformance

A cached prefix expires 5 minutes or 1 hour after the request that last used it. The next request writes the whole prefix again at the write price. A change near the top of the prefix, such as a timestamp in the system prompt, forces the same rewrite with no wait at all.

5.6%of the sample, the premium on 588 rewrites after an idle gap
Sample
  • 489 of the idle gaps lasted 5 to 60 minutes on the 5-minute TTL, at 3.7%. A keep-alive read every 4.5 minutes during those waits would have cost 0.3%.
  • 456 gaps lasted 5 to 15 minutes, the pattern of a parent run waiting on a subagent. This is the Optimization page's "Idle while parked" cause.
  • 203 rewrites came with no idle gap, a changed prefix, at 1.1%.
  • The 1-hour TTL cost 5.5% extra on writes and avoided 12.4% in rewrites across 961 gaps. For this fleet the detector's answer is to keep it.
Lever
  • Recommend a TTL per agent from its gap pattern, including the answer "keep it".
  • Offer a keep-alive while a parent waits on a subagent, sent by the model proxy on governed calls, off until the owning team turns it on.
  • Report each bust with the line of the prefix that changed.
Finding text

<agent> waited 5 to 15 minutes <n> times, and each wait rewrote a <k>-token cache. A keep-alive would have cost <a> against <b> in rewrites.

Signals
Cache write tokens by TTL (5 minutes, 1 hour), cache read tokens, request timestamps, prompt_cache_ttl, context size
Formula
A write of at least half the context is a rewrite. It is idle if the gap since the last request passed the TTL, and a bust otherwise. Its premium is context × (write_price − read_price). A keep-alive costs floor(gap ÷ 4.5 min) × context × read_price.
Retention
Works on digest_only.
Today
cache_writes_never_read ships and is the only cause list_waste returns. Cache misses, cache hit rate under 72%, and cache writes over 6% of input are specced.
Gap
No per-turn digest of the system context, so a bust cannot be traced to the line that changed.
4

Model class fit

Newdigest_onlyEfficiency

A run that reads, searches, and reports but never changes a file may not need a complex-class model. The detector finds those runs and prices them on a light-class model, as an estimate.

17.3%of the sample, spent by 1,007 subagent runs that made no edits
Sample
  • On Sonnet 5 those runs would cost an estimated 31% less, 5.4% of the sample. On Haiku 4.5 they would cost an estimated 66% less, 11.3%.
  • Opus 5.5 and Sonnet 5 charge the same for a cache read. For read-heavy runs the saving comes from output and cache writes only.
  • 54% of requests ran at xhigh effort and 1% at max.
  • The 13 spin-loop runs are left out, so detector 1 keeps their spend.
Lever
  • Propose a model route for the agent or the task class in the run's tuple, through a steering record PR.
  • Propose an effort level per task class.
  • Replay a sample of the runs on the light class, with the owning team's approval because the replay spends. The replay turns the estimate into a measurement.
Finding text

<agent> ran <n> runs on <model> that changed no file. On <light model> they would have cost an estimated <amount> less.

Signals
subagent_model, subagent_total_tokens, tool_is_mutating, effort, session_files, tokens by cost class
Formula
For each run with no mutating call, reprice its tokens by class at the light-class prices. The card labels the result an estimate until a replay confirms it.
Retention
Works on digest_only.
Today
Nothing ships. The Optimization page's recommendation on reasoning over 40% of output on a flagship model is the nearest spec.
Gap
No step classification. A run that edits one file after an hour of reading counts as an edit run, so the detector misses it.
5

Context carry

Ships in partdigest_onlyEfficiencyPerformance

A tool result stays in the context until the run compacts, and every later request re-reads it. A 10,000-token listing read at step 5 of a 200-step run is paid for 195 more times.

1.9%of the sample, re-reading 2,033 results of 5,000 to 20,000 tokens
Sample
  • Requests over 150,000 tokens of context took 64% of spend.
  • One result passed 20,000 tokens. Claude Code caps its own tool output, and tools from an MCP provider have no cap, so the shipped unpaged_results finding matters most for MCP tools.
  • The carry stops at the next compaction. The sample held 774 compactions.
Lever
  • Set a result cap per tool in MCP Studio, with paging.
  • Propose earlier compaction for runs that stay over 150,000 tokens.
  • Propose a fresh subagent for a separable step, so its reads never enter the parent's context.
Finding text

<tool> returned <n> results over 5,000 tokens. Later requests re-read them <k> times, at <amount>.

Signals
tool_result_tokens, mcp_server_name, compaction tokens before and after, context_window, request order
Formula
result_tokens × read_price × requests_until_next_compaction for each result over 5,000 tokens.
Retention
Works on digest_only.
Today
unpaged_results ships. It reprices results over 20,000 tokens at a 4,000-token page. Context bloat and tool results over 30% of input are specced.
Gap
productive_ratio is null, so the detector cannot tell a result the agent used from one it ignored.

Prompt habits

Speccedcontent_exactEfficiencyMaintainability

The prompts a run receives show where agents keep being told the same thing: a correction, a pasted block of rules, an interrupt. Each repeat is steering that lives in a clipboard or a template instead of a record.

2.4%of the sample at most, the turns before 151 interrupts
Sample
  • 15 prompts read as corrections. Their turns cost 0.2%.
  • 38 prompts ran over 8,000 characters, about 180,000 tokens together.
  • 16 paragraphs were pasted into 2 or more runs. 106 sentences were reused in 3 or more runs, 3,445 times in all.
  • Most of the repeated text came from a scheduler, from messages between agents, and from workflow templates. So the detector must know who sent each prompt.
  • The median run had 1 prompt, so this sample cannot size the habit cost. The Optimization page's corrective prompts figure stays a design placeholder until customer data sizes it.
Lever
  • Turn a repeated instruction into a steering record proposal through open_steering_pr, with the runs that repeated it as evidence.
  • DecidedReport habits per operator, per agent, and per workspace. Write each one as a rule the operator can adopt, with its definition beside it.
  • DecidedRank operators by unproductive spend for managers. The ranking and the figures beside each name are in Operator productivity.
Finding text

Runs received "<sentence>" <n> times this month. A steering record would reach every run it applies to with no paste.

Signals
Prompt text, prompt_digest, prompt_length, prompt_source, prompt_origin, command_name, is_meta, interrupted_message_id
Formula
Cluster prompts by sentence digest across runs. A cluster in 3 or more runs is a steering candidate. A correction or an interrupt is priced at the turns between the prompt it answers and itself, an upper bound.
Retention
Needs content_exact. On a digest_only workspace the card reads "Needs prompt text" and shows whole-prompt repeats only.
Today
Corrective prompts and two operator habits are specced on the Optimization page. No detector backs them.
Gap
prompt_source and prompt_origin come from Claude Code only. On other harnesses the detector cannot tell a person from a scheduler.

Recurring runs

Newdigest_onlyEfficiency

A scheduled job sends the same prompt on a clock. When nothing changed since the last run, the run pays to find that out.

1.8%of the sample, from one scheduled prompt that ran 602 times in 7 days
Sample
  • The median run of that job cost $0.32.
  • 56 of its runs changed no file.
Lever
  • Start the job on a change, such as a new commit or a new issue, instead of on a clock.
  • Lower the frequency, or move the job to the light class.
  • When the job calls the API directly and can wait, send it as a batch at half price.
Finding text

<n> runs started with the same prompt this week. <k> of them changed nothing, at <amount>.

Signals
prompt_digest, prompt_source, run start times, session_files digests, tool_is_mutating, run cost
Formula
Group runs by the digest of their first prompt. A group of 5 or more runs is recurring. Its unproductive spend is the cost of the runs with no mutating call and no file change.
Retention
Works on digest_only.
Today
Nothing ships or is specced.
Gap
Harnesses that do not report prompt_source cannot mark a run as scheduled, so grouping falls back to identical first prompts.

Rules

Counting

The Optimization page shows one total. These rules keep that total honest when detectors overlap. Rules 1 and 2 are decided, and rules 3 to 5 are proposed.

  1. Whole requests onlyDecided

    The headline total adds detectors 1, 7, and 8, which price whole requests. A request counts once, under the first of those detectors that claims it.

  2. Parts on their own cardsDecided

    Detectors 2, 3, and 5 price a part of a request: the prefix, the write premium, or the carry. Each shows its own figure beside the total and stays out of the sum.

  3. Estimates labelledProposed

    Detector 4 is a counterfactual. Its card says "estimated" and names the model it repriced against until a replay confirms it.

  4. Absent, never zeroProposed

    A class a harness does not report shows as absent. A detector that needs content_exact reads "Needs prompt text" on a digest_only workspace.

  5. Shares firstProposed

    Each card leads with its share of the workspace's spend and a per-unit price, such as a weekly price per 1,000 tokens. The amount follows.

Operators

Operator productivity and work orders

Unproductive spend prices the steps that bought no progress. A manager also needs the other side: what each operator's agents finished. More agents is better when output rises with them and the unproductive share does not. A work order with a definition of done gives each figure below an exact count, because its checks pass or fail.

Operator ranking

  • DecidedSpend ranks operators by unproductive spend, highest first, for the period and the workspace in view. Managers see the ranking.
  • ProposedEach name shows its unproductive spend, its unproductive share, its done work orders, and its unassigned share. The share and the done count separate an operator who wastes from one who runs more agents.
  • ProposedEach figure links to its definition and to the runs behind it. The ranking reports the record and adds no verdict.
  • ProposedA workspace setting replaces names with stable pseudonyms where a works council or local law requires it. The figures stay.

Output

Proposed Output is done work orders. For these metrics, a work order is done when every item's definition of done passed its checks. Runs, commits, and merged PRs are not output on their own. A person still accepts each item. A work order with no definition of done counts toward spend and toward the assignment figures, and stays out of every done metric.

Unassigned spend

Every run has a parent work order (D2). A run an operator starts outside Oxagen gets a direct work order, and the operator can attach it to a work item later. Spend on a direct work order that no one attached to a work item has no assignment behind it.

  • ProposedUnassigned spend: tokens and dollars on runs whose direct work order has no work item, per operator, per agent, and per workspace, with its share of all spend.
  • ProposedUnassigned trend: that share week over week. It falls as work moves onto work orders.
  • ProposedUnassigned spend shows as its own line beside unproductive spend and stays out of the unproductive total. A run with no assignment can still be useful work.
  • ProposedA direct work order attached to a work item within a grace window counts as assigned from its first run.

Capture needed

  • Each run carries its work_order_id (wedge Open decision 5).
  • Each check run of a definition of done is recorded with its work order, result, and time.
  • Each direct work order records when it was attached to a work item.
  • Run open and close times per agent give agents in flight.

Plan

Build order

The order puts detectors that run on existing fields first, and capture work before the detectors that need it.

  1. Reprice repeats and add spin loops

    Change duplicate_tool_calls and repeated_shell_commands to the request price, add a loop finding, and add the no-progress limit in observe mode.

  2. Operator ranking

    Rank operators by the unproductive spend step 1 prices, and add each detector's figure as it lands.

  3. Recurring runs

    Group runs by prompt_digest and price the runs that changed nothing.

  4. Cache expiry and the TTL answer

    Price idle rewrites and busts, estimate the keep-alive, and give each agent a TTL recommendation.

  5. Context carry

    Extend unpaged_results to price results over 5,000 tokens up to the next compaction.

  6. Model class fit

    Reprice read-only runs, and add a replay the owning team approves.

  7. ADR-062 capture

    Report the three token source fields and a per-turn system digest, then split standing context by source and trace each bust.

  8. Prompt habits

    Cluster repeated instructions on content_exact workspaces and open steering record proposals.

  9. Outcome capture

    Persist the PR, CI, and revert result per run, then price spend with no outcome.

  10. Work order capture

    Record work_order_id on each run and each check run of a definition of done, then report the operator metrics, the work order metrics, and unassigned spend.

Limits

  • The spend is the harness's reported token usage at list price. It is not a bill.
  • 1,105 requests carried no model price and count as zero.
  • No long-context premium is priced.
  • Standing context is an upper bound, because the first request's context includes the first prompt.
  • A repeat's round-trip price is the carrying request's cost divided by the tool calls in that request.
  • Interrupt and correction costs are upper bounds.
  • This is one operator's fleet, heavy on background jobs and subagents. A customer's mix will differ, and the ranking weighs reach for that reason.
